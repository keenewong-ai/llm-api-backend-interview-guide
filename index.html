點樣用呢份指南

面試官問 LLM API Backend 相關問題，通常唔係考你記唔記得 API 參數，而係想知道你有冇喺 production 遇到過（或認真思考過）以下情況：

  • Rate limit 突然爆發時點樣避免雪崩
  • Streaming 中途斷線或失敗點樣處理
  • 點樣確保 LLM 輸出可以可靠地被程式 parse
  • RAG 答錯嘢、引用舊資料點 debug
  • 成本、延遲同可靠性之間點樣取捨

每個課堂都包含四個固定部分：面試官真正想問嘅嘢、生產環境現實、解決思路，同埋現實例子 + code（Python / TypeScript）。完成之後撳「標記為已完成」，進度會記喺呢部瀏覽器，重新整理都唔會消失。

Code 例子以講解概念為主，model 名稱、API 欄位同價錢可能隨時間改變，實際使用請以各 provider 官方文件為準。

七堂課

跟住順序讀最好，每堂都可以獨立溫習。進度會自動保存在本機瀏覽器。

L01 429 Rate Limit 429 唔係 bug，係常態。重點係點樣「有禮貌咁」重試，同埋喺自己系統入面先做好 admission control。 L02 Streaming Streaming 令用戶好快見到第一個字（TTFT），但同時帶嚟斷線、buffering、backpressure 等一堆工程問題。 L03 Structured Output LLM 本質係生成文字，但 backend 需要可以 parse 嘅資料。重點：schema 約束 + 驗證 + 失敗重試。 L04 RAG RAG 嘅質素 80% 取決於 retrieval，而唔係 LLM。Garbage in, garbage out。 L05 Fallback & Routing 冇任何一個 provider 係 100% uptime。Production 要假設佢會慢、會錯、會限流。 L06 Caching 最平、最快嘅 LLM call 就係唔使 call。但 cache 錯咗嘅答案比慢更差。 L07 LLM Gateway 當公司有多個團隊、多個 provider，就需要一個中央入口統一管理 auth、限流、成本同觀測。

面試答題小貼士

  • 先澄清需求（QPS、latency target、cost budget、是否需要 streaming、合規要求）
  • 講 trade-off，而唔係只有「正確答案」
  • 提到 production 現實（429、streaming 斷線、cost、observability）會加分
  • 如果有真實經歷，優先用故事回答（STAR：Situation、Task、Action、Result）
  • 主動提到你會點樣測量同監控，同埋點樣驗證改動有效
  • 唔識嘅就坦白講，再講你會點樣搵答案 / 做實驗
