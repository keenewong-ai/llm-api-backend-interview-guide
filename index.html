1. 處理 429 Rate Limit

面試官真正想問嘅嘢

「你有唔有真正處理過 production 429？你知唔知 rate limit 同 spend limit 嘅分別？你點樣避免 retry storm？」

生產環境現實

  • OpenAI / Anthropic 同時有 RPM（requests per minute）同 TPM（tokens per minute）限制
  • 長 context 或大 output 嘅 request 好容易打爆 TPM，即使 RPM 好低
  • 盲目同步 retry 會造成 thundering herd，令情況更差
  • Streaming request 中途 429 特別難搞，因為已經開始返咗部分 response

解決思路

  1. 區分可重試（429 rate limit）同不可重試（spend cap、invalid request）
  2. 用 exponential backoff + jitter
  3. 尊重 Retry-After header
  4. 用 queue / semaphore / token bucket 做 upstream control
  5. 監控 remaining tokens，提早降速

現實例子 + Code

情境：你嘅服務突然收到大量用戶請求，開始收到 OpenAI 429。你需要一個可靠嘅 retry wrapper。

import time
import random
import httpx
from typing import Callable, Any

def is_retryable_error(response) -> bool:
    """判斷係咪可以重試嘅錯誤"""
    if response.status_code != 429:
        return False
    
    # 有些 429 是 spend limit，不應重試
    error_code = response.json().get("error", {}).get("code", "")
    if "spend" in error_code or "quota" in error_code:
        return False
    return True

def call_with_retry(
    func: Callable,
    max_retries: int = 5,
    base_delay: float = 1.0
) -> Any:
    """帶 jitter 嘅 exponential backoff"""
    for attempt in range(max_retries):
        try:
            response = func()
            
            if response.status_code == 200:
                return response
            
            if not is_retryable_error(response):
                response.raise_for_status()
            
            # 讀 Retry-After，如果有嘅話
            retry_after = response.headers.get("Retry-After")
            if retry_after:
                delay = float(retry_after)
            else:
                delay = base_delay * (2 ** attempt)
            
            # 加 jitter 避免所有 client 同時重試
            jitter = random.uniform(0, delay * 0.3)
            time.sleep(delay + jitter)
            
        except httpx.RequestError as e:
            if attempt == max_retries - 1:
                raise
            time.sleep(base_delay * (2 ** attempt))
    
    raise Exception("Max retries exceeded")

# 使用例子
def make_llm_request():
    return httpx.post(
        "https://api.openai.com/v1/chat/completions",
        headers={"Authorization": "Bearer sk-..."},
        json={
            "model": "gpt-4o-mini",
            "messages": [{"role": "user", "content": "Hello"}]
        },
        timeout=30.0
    )

result = call_with_retry(make_llm_request)
print(result.json())

面試時可以再補充：實際生產會用 queue（例如 Redis + worker）做 admission control，而唔係只靠 client-side retry。

面試答題小貼士

  • 先澄清需求（QPS、latency target、cost budget、是否需要 streaming）
  • 講 trade-off，而唔係只有「正確答案」
  • 提到 production 現實（429、streaming 斷線、cost、observability）會加分
  • 如果有真實經歷，優先用故事回答
  • 主動提到你會點樣測量同監控
